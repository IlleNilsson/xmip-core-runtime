# xmip-core-runtime

The Xmip runtime: a node started from its configuration and the technologies its program links, the message path it runs, and the operate plane's two ends.

**A node running.** A program starts a node by `running::activation::started(path, linked, program)`, the order its startup owns (ADR-0031, amendment 2026-11-12): its trust first, running only a slice its cluster's authority signed for it (`signed`: the authority, the node's name and the highest serial seen are pinned in `<stem>.pin.toml`, apart from its active configuration, `<stem>.active.xmip`, the last slice that ran, both private files in the data directory beside the configuration folder, whose names and the pin's form are `configure::signed`'s; a swapped certificate, an older slice or another node's is refused, and a candidate above the serial seen is pinned as seen before anything reads it; the trust reads `node.xmip` itself and nothing reads it before, so a candidate absent or unreadable is refused there like any other, tried again at the next start, while the active configuration runs, ADR-0031, amendment 2026-11-19); then an attempt over the candidate, `running::Running::start(path, attempt, linked)` and the program's own steps that can refuse, serving nothing; then `Running::activate`, which keeps the slice as the active configuration and only then serves. A candidate refused at any step is let go — its Storage node stopped as it is dropped (`storage::Reached`) — and the same attempt is made over the active configuration in the same process; only with none that starts is the start refused. Which slice runs, and why another did not, is the node's record at `<node>/configuration` (`running/activation/standing.rs`), which `xmip-service --activation` reads back; whether the node is ready — it runs that slice and its Xmip Storage stands Fine at `<node>/storage`, a Storage node of several the primary or a standby ready and following, handed a frame by its primary — is `running::activation::readiness` (`running/activation/readiness.rs`, over the one read of its publication, `published.rs`), which `xmip-service --readiness` asks before a deploy restarts the next node (ADR-0056, amendment 2026-11-23). `Running::start` runs ADR-0018's nine startup phases (`src/running.rs`, the phases' work in `src/startup.rs`, their names in `src/service.rs`): it reads the slice's text and every Xmip Application it binds, each the configuration's `[[xmip_applications]]` section of its name (`start::parsed`, the one reading; `start::read` reads the slice a node would try first, writing nothing, for whoever reads without running), builds and validates the execution tree — the bound Receive Ports with each Receive Location's depth, the Send Ports it takes with their policy, and the Work Processes bound to it, each started with its design's `module`, `unit` and settings, among it — with every Location held to its technology's settings declaration, and refuses — before anything serves — an address whose scheme no linked transport declares, an accepted mechanism or a filter name the program was not built with, an accepted Party `[[parties]]` does not declare, a `[provision.receive]` that does not read (`src/receive_certificate.rs`), a contract at a Location (arrival holds no Stream to one yet), and a Module needing a Host Service in a process of its own. It plans the Host Services the started Modules need (`src/host.rs`, one host-type rule: what a Module is written in), loads each technology the configuration uses once — carrying its declaration into the catalogue — and opens each `[[modules]]` library once through the C ABI, its `library_path` read against the folder the configuration is in and a module holding only Work Process units only where a Work Process the node starts names it (`src/library.rs`, behind `dynamic-loading`; a unit generated from a design, the example `approval_unit`, is opened and turned in its tests), registers every capability once (`src/capability_registry.rs`), builds each Location's transport once from its address and settings and gives it the node's location as it does (`transport::Configured::open`, then `Configured::on_node` with `running::publication::location`, the owner's *Option A*, 2026-10-03 — the file transport claims in that name and returns what it still held there; so a Receive Location keeps its listener or session between receives) and the guard its receives terminate TLS with, the node's `[provision.receive]` certificate and anchors (`Configured::guarded_by`; a Location asking for TLS on a node with none is refused), and a Receive Location's listener bound (`Configured::listening`, through `linked::built_on`, never for a Send Location; the owner, 2026-11-16, *Bind at open*; ADR-0018, amendment 2026-11-16), so a node listens when its start returns and a caller that connects at once is taken on its first connect, and a port that is taken refuses the start at phase 9, naming the Location, the address and the port — until 2026-11-16 the first receive bound it, after the start, and every test that sent to a node it had just started asked again through a fixture deleted that day; reaches Xmip Storage (`src/storage.rs`, below), builds the `Runtime` once — the route gathering compiled then (ADR-0066) — and, once activated, serves every Receive Location on a thread of its own: `Receiving::serve` (`src/receiving.rs`) takes what arrives — at most as many arrivals as the Location's pool has threads free and the node's carry budget has places (`Transport::receive_up_to`), waiting for a place where the node has none, the rest left at the far end (`src/budget.rs`: `budget::NodeBudget`, the node's `Budget`s beside each pool — the arrivals carried at once across every Location and the bytes they hold, and the bytes the sends hold; `tests/ledger/roomed.rs`; open problem 38, 2026-10-19) — and carries each arrival on the Location's pool (`src/pool.rs`: a dynamic, bounded pool of scoped threads, never below one, growing while work waits up to `pool::Limits::per_hardware_thread` — for a Receive Location twice the machine's hardware threads (`pool::hardware_threads`), calculated as the node starts — and shrinking after a minute idle; `publication` (`src/running/publication.rs`) is that snapshot at the node's `location`, `xmip:///<cluster>/node/<name>` — itself, its System Process, what it declares, each module, Location and Subscription, the figures at the stage that counts each kind, its Subscriptions' standing, and each Receive Location, Send Port and Send Location whose `start` says `false` — known, opened by nothing, Done and saying `configure::NOT_STARTED`, "not started: the configuration says false" (`ExecutionTree::not_started`; the owner, 2026-10-13; ADR-0064, amendment 2026-10-28) — with the node drawn by `observe::topology::draw` and `party`, the node saying the roles its configuration declares, the Party facing it on each side, *TX-Party 1* sending into it and *RX-Party 1* it delivers to (`party::facing`; ADR-0052, amendment 2026-11-13), every link named by `observe::topology::link_id`; its own publication relates it to no other node, which the cluster's drawing does by role (`observe::topology::relate`) — a standby not ready yet publishing its `<node>/storage` Working — and what moved over the drawing — each link's rate and each drawn thing's activity, per second over the last thirty seconds — stated by the `observe::topology::window::Window` its publisher keeps and hands `publication` every time (ADR-0018, amendment 2026-11-10); `running::publication::stopped` (`src/running/publication/stopped.rs`) is what it leaves once drained, the node Done, drawn still, and its pauses and what it never started standing. `xmip-service` writes it to `<data>/snapshot.xmip` (ADR-0018, amendment 2026-09-30).

**Its membership of the cluster** (`src/membership.rs`; ADR-0056, amendment 2026-11-13). A node activated writes its row of Xmip Storage's `membership` table once Storage is reached, tried again each `[tuning] storage_pass_over` until it is, and again as it stops in order, before its own Storage node stops (`membership::Joined`), where its Storage client already knows Storage answers (`storage::Reached::answers`, the rule `<node>/storage` stands by) — where it does not, the stop is not written, nothing waits on Storage, and `Outcomes::membership` says why in the node's stop record, so a stop never waits out a Storage node's timeout (`tests/measured/membership.rs`). Its stop updates its own row alone, which stays its node's latest or not as Xmip Storage keeps it, so a successor started meanwhile stays the member (`XmipStorage::write_member`; ADR-0056, amendment 2026-11-19). Each start is numbered by its node as its process is drawn, above the number its start file keeps and never below the node's Clock (`membership::numbering::numbered`, `xcore::clock::serial`), the file, `<stem>.start.toml` beside its pin (`configure::start`), kept before its row is first tried, so a crash, a clock set back or a store lost or restored never numbers a start below one before it while the clock is right; Xmip Storage registers a start only above its node's latest, and one refused as superseded — its first write landing after a later start registered — floors its start file at that start's number (`numbering::floored`), so the node's next start registers whatever its clock says, tries nothing more, follows nothing and writes no stop, and keeps serving, its successor the member (ADR-0056, amendment 2026-11-20). The row says its scope, the roles `[nodes.<name>] roles` declares and that declaration's evidence with its online capability, its operate listener's network address as bound (`Running::operate`), its sync address (none until a node starts a sync listener, ADR-0065), its place among the Storage nodes as its own Storage node of several finds it by the process it answers as (`storage::Reached::placing`, `StorageNode::place`), the save and serial of the slice it runs, its process, drawn new at each start, and its start's number. A Storage node of several writes through the Xmip Storage it holds for its own work. Once written, the node follows the table through Xmip Storage's wait (`Watched::Membership`), reading the members each time a row is written and never asking again meanwhile (`membership::Followed`, raising its `revision`); `Followed` is the `xcluster::Membership` every follower of the members takes, `Running::membership` hands it out, and each member's capability is read back from its evidence by `node::Capability`'s one reading. The node says it at `<node>/membership`: Working until its row is in Xmip Storage, Fine with since when, where it answers and the save it runs, and Stressed where that save is not its peers' — the one most running members run, alone at the most (`membership::peers_save`; ADR-0031, amendment 2026-11-13) — and Done where a later start of its node is the member: its own refused as superseded, in Xmip Storage's words, or registered before a successor that runs beside it, naming that start (ADR-0056, amendment 2026-11-20).

**What the program links.** The runtime names no technology (`architecture.toml`: a platform service depends on no technology repository). The program that starts a node hands over what it was built with as `linked::Linked` — its transports (`LinkedTransport::of::<T>()` over `transport::Configured`), route technologies, authenticators, policies and identifiers, and the policies set up from the Locations a node starts (`Linked::location_policies`, each handed, as the node starts, the gates of its Receive Locations and its Send Locations, `linked::Started`; ADR-0068, amendments 2026-10-19 and 2026-10-20) — and the node takes what its configuration names (ADR-0025). Every send from a Send Location names the target its technology gives for the Location's address (`LinkedTransport::target`, `transport::Configured::own_target`): the address in the technology's own terms, or the empty target where the address names only the server and a setting the destination — a Kafka topic, an MQTT topic, a queue — which the technology reads as that destination (ADR-0064, amendment 2026-11-10). ADR-0018's amendment of 2026-09-26 makes that program `xmip-service`, an executable of the estate's root crate that links technologies by build feature. It was built on 2026-09-28. It runs a node until the operating system's service manager or the console stops it, then calls `Running::stop`. The runtime's own tests are a program too: they link `xmip-core-transport-tcp` and start a node that receives and sends over loopback. Every Location's transport is given what its node hands it once, as it is built — its location, pins, the node's one `transport::Sharing`, its turn, guard and secret, and a Receive Location's listener bound (`tests/running/listening.rs`: over TCP and HTTP a caller connecting the moment the start returns is taken on its first connect, and a port another holds refuses the start at `accept-work`, naming it) — by `linked::built_on`, which `linked::open` builds through and a test's opener calls for a transport it built its own way: `tests/running/sharing.rs` builds two serial Locations naming one device on a bench port (`serial::bench`) and proves they are handed one sharing and go through the device's one port (ADR-0064, amendment 2026-11-15). The stand-ins they run a node's gates with — an authenticator verifying with the verdict it was given, a policy allowing what the gates authenticated — are `fixture`, placed once behind the `test-support` feature, which only the crate's dev-dependency on itself enables, so its unit tests and its test programs (`tests/ledger`, `tests/plane`, `tests/running` and the timing program `tests/measured`) share them. `Running::cluster` and `Running::node` give the node's place, and `Running::location` the location `xmip-service` declares, `xmip:///<cluster>/node/<node>` (ADR-0053).

**As a service.** `src/registration.rs` is the one place that writes what a service manager is told about a node's Xmip Service: a systemd unit (`Type=notify`, `Restart=on-failure`, `RestartPreventExitStatus=` the refused exit code `REFUSED`), a launchd property list, or the `sc.exe create` arguments and the settings that finish them (`windows_service_settings`: the description, and the environment the service is handed, such as `XMIP_AUDIT_DIRECTORY`). It runs `xmip-service --configuration <path>` under the name `node_service_name(node)`, `xmip-<node>`, and quotes a path that has a space. `xmip-service --definition` prints it, and `xmip-service --install`, which every package runs, applies it (ADR-0015, amendment 2026-10-13). `src/service_control.rs` asks this platform's service manager to start or stop a node's installed service by that name: `sc.exe`, `systemctl --no-block` or `launchctl`, chosen at compile time. It returns when the manager has accepted the request, and a manager's refusal comes back in the manager's own words. Nothing in the runtime applies a registration or restarts a service.
