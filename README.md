# xmip-core-runtime

The Xmip Service and the Xmip Host Services it supervises: configuration, execution tree, startup validation, host-process planning, and capability and Module registries.

The runtime composes capabilities and invokes Handlers through the application binary interface (ABI). Technology implementations remain in their capability repositories.

Its native library is what the operator surfaces load (`xmip_operate.h`): the table they read a node through, starting and validating a node, section 7 — the rules a surface calls instead of keeping its own — section 8, a publication read for a surface, section 9, a program's audit record, and section 10, an Xmip Application read and edited for the routes designer. `src/ffi/rule.rs` and `src/ffi/rule/node.rs` forward each rule to the crate that owns it (`observe::Scope`, its containment, parts, node and stage, `observe::Health`, `observe::Standing`, `observe::Counted`, `observe::capability`, `node::Stage`, `node::Capability`), one call per export and no rule of its own; `src/ffi/publication.rs` reads a publication by `observe::Publication` and hands it out as the header's values (ADR-0027 and ADR-0052, amendments 2026-09-24), and `src/ffi/topology.rs` says what a topology kind, origin or pattern is called, forwarding `observe::topology`'s `word` and `name` (ADR-0052, amendment 2026-09-25). `src/ffi/audit.rs` forwards `xmip_audit_v1` to `xmip-core-audit`'s `ProgramAudit`, so a .NET program and PowerShell audit through the one capability every Rust program calls directly; the record, the file sink and the fallback to the operating system's log stay the capability's (ADR-0062; ADR-0027, amendment 2026-09-25). `src/catalogue.rs` holds the technologies this runtime carries and the settings each declares (ADR-0064, amendment 2026-09-26): whatever brings a technology into the runtime hands over its declaration with `catalogue::carry` — the runtime names no technology — and every Location, the node's own and every bound one, is held to its technology's declaration at validation and start through `configure::location_problems`; `src/ffi/catalogue.rs` answers the same declarations through `xmip_technology_catalogue_v1` (section 12) for the language server and the desktop editor. `src/ffi/process.rs` forwards section 13, a System Process declared (ADR-0053): `xmip_process_declare_v1` to `node::Declaration` and `xmip_process_declarations_v1` to `node::standing`, answered as the header's JSON, so a .NET program and the estate's PowerShell declare and list processes through the node and write or read no declaration file of their own. The Message treatments are `xmip-core-message`'s (`MessageTreatment::CONVERSATION`, `BUSINESS`, `PASS_THROUGH`); `src/generation.rs` keeps only what a generation is.

A node that binds Xmip Applications (ADR-0064) is given them: `build_execution_tree` takes the node's document and the Applications, and `configure::bind` answers what the node runs — the bound Locations whose `node` is this node, and every Subscription of every bound Application, which the tree carries as `subscriptions` for routing to ask. `xmip_start_v1` reads each bound Application from the path its binding names, relative to the configuration file; `xmip_validate_v1` reads either document, an Application as a design and a node's bindings as far as they say on their own. Section 10 of `xmip_operate.h` is the routes designer's: `src/design.rs` reads the JSON a surface hands over into `configure`'s types and writes `configure`'s answers — an Application's routes, a filter's structure and text, an edit — and `src/ffi/design.rs` holds the four exports, `xmip_application_routes_v1`, `xmip_filter_structure_v1`, `xmip_filter_text_v1` and `xmip_application_edit_v1`; no rule is written in either.

Section 11 of `xmip_operate.h` is Events, subscribed from any language (ADR-0065): `src/ffi/event.rs` holds the six exports — `xmip_event_subscribe_v1`, `xmip_event_listen_v1`, `xmip_event_next_v1`, `xmip_event_batch_free_v1`, `xmip_event_unsubscribe_v1` and `xmip_event_publish_v1` — each a thin forwarder into `xmip-core-event`'s process hub (`Hub::process`), and `src/ffi/event/header.rs` reads and writes the header's Event and filter and holds its action and outcome numbers against `node::Stage` and the event crate's `Outcome`. The matching rule, the authorization gate, the bounded queue and the audit are the event crate's; a drained batch owns what it hands out until it is freed.

Arrival (`src/arrival.rs`) promotes every name the Subscriptions' filters use through `route::promote` and the route technologies loaded (`Runtime::route_sources`), before a Journey opens: a bare name is context, a prefixed one (`header:`, `party:`, …) is read by its technology, a Null is absent, and bytes or a prefix no loaded technology provides refuse the Message (`Refused::Promotion`; ADR-0046, amended 2026-09-24). Each filter is one line of Xmip's expression language, compiled as its Application is read, so a node binding one that does not compile is refused as it starts (ADR-0066); `route::publish` decides the compiled tree, and a value that is not there is unknown, with its reason, never a silent false.

The C boundary is one folder, `src/ffi/`, and the only place in the runtime that may hold unsafe code (ADR-0050, refined 2026-09-25): the operator's table (`ffi/operate.rs`, over `operator.rs`, which holds what a table reads and what is published), starting and validating (`ffi/start.rs`, over `start.rs`), sections 7 to 13, and the loader that opens a module's library (`ffi/loaded_module.rs`, `ffi/loaded_contract.rs`, ADR-0057). What a boundary file does beyond reading and writing pointers stays outside the folder. `test/Unsafe.Test.ps1` holds it.

`architecture.toml` carries the maturity; this file does not repeat it.
