# xmip-core-runtime

The Xmip runtime: a node started from its configuration and the technologies its program links, the message path it runs, and the native library the operator surfaces load.

**A node running.** `running::Running::start(path, linked)` runs ADR-0018's nine startup phases (`src/running.rs`, the phases' work in `src/startup.rs`, their names in `src/service.rs`): it reads the node's configuration and every Xmip Application it binds (`start::read`), builds and validates the execution tree with every Location held to its technology's settings declaration, and refuses — before anything serves — a transport, an accepted mechanism or a filter name the program was not built with, a contract at a Location (arrival holds no Stream to one yet), and a Module needing a Host Service in a process of its own. It plans the Host Services the started Modules need (`src/host.rs`, one host-type rule: what a Module is written in), loads each technology the configuration uses once — carrying its declaration into the catalogue — and opens each `[[modules]]` library once through the C ABI (`src/library.rs`, behind `dynamic-loading`), registers every capability once (`src/capability_registry.rs`), builds each Location's transport once from its address and settings (`transport::Configured::open`, so a Receive Location keeps its listener or session between receives), builds the `Runtime` once — the route gathering compiled then (ADR-0066) — and serves every Receive Location on a thread of its own: `Receiving::serve` (`src/receiving.rs`) takes what arrives and `message_path::carry` runs each Stream through arrival, routing and departure. `stop` drains: each Receive Location takes nothing more once its current receive returns (the technology's own wait bounds it), what it took is carried whole, then the transports and loaded Modules are let go. `outcomes` and `snapshot` say what became of every Stream and what the node is doing.

**What the program links.** The runtime names no technology (`architecture.toml`: a platform service depends on no technology repository). The program that starts a node hands over what it was built with as `linked::Linked` — its transports (`LinkedTransport::of::<T>()` over `transport::Configured`), route technologies, authenticators, policies and identifiers — and the node takes what its configuration names (ADR-0025). ADR-0018's amendment of 2026-09-26 makes that program `xmip-service`, an executable of the estate's root crate that links technologies by build feature. It was built on 2026-09-28. It runs a node until the operating system's service manager or the console stops it, then calls `Running::stop`. The runtime's own tests are a program too: they link `xmip-core-transport-tcp` and start a node that receives and sends over loopback. `Running::cluster` and `Running::node` give the node's place, which `xmip-service` declares as `xmip:///<cluster>/node/<node>` (ADR-0053).

**As a service.** `src/registration.rs` is the one place that writes what a service manager is told about a node's Xmip Service: a systemd unit (`Type=notify`, `Restart=on-failure`, `RestartPreventExitStatus=` the refused exit code `REFUSED`), a launchd property list, or the `sc.exe create` arguments. It runs `xmip-service --configuration <path>` under the name `node_service_name(node)`, `xmip-<node>`, and quotes a path that has a space. `xmip-service --definition` prints it. `src/service_control.rs` asks this platform's service manager to start or stop a node's installed service by that name: `sc.exe`, `systemctl --no-block` or `launchctl`, chosen at compile time. It returns when the manager has accepted the request, and a manager's refusal comes back in the manager's own words. Nothing in the runtime applies a registration or restarts a service.

**The message path.** Arrival (`src/arrival.rs`) runs the transport gates against the Receive Location's `ReceiveGate` — the closed set of mechanisms its configuration's `accept` names (ADR-0019 clause 1), each verified by a linked authenticator — then creates the Message, runs the message gates, promotes every name the Subscriptions' filters use through the `route::Gathering` the Runtime was built with (a bare name is context, a prefixed one is read by its technology, a Null is absent, bytes refuse the Message; ADR-0046), opens the Journey and publishes. Departure (`src/departure.rs`) resolves each destination to the node's Send Locations (`src/sending.rs`: a bound Send Port is the Send Location of its name, a Send Port Group reaches its Ports together), authorizes again, resolves whose identity the chain declares (ADR-0006) and sends through the Location's transport; an Xmip Process destination is `ProcessNotRun`, since a Process is compiled at design time and none is built (ADR-0066 clause 4). What both halves share — the `Runtime`, `Parties` and `PartyDirectory` — is `src/message_path.rs`; its `clock` is read at each gate, and a running node's is `xcore::SystemClock`. The Message treatments are `xmip-core-message`'s; `src/generation.rs` keeps what a generation is.

**For a surface.** Its native library is what the operator surfaces load (`xmip_operate.h`). `start::start`, behind `xmip_start_v1`, is the first three phases alone: it validates and plans a node against the technologies this runtime carries and says in every record that nothing runs, since a surface's process links no technology (whether it may run a node at all is open problem 20); `xmip_validate_v1` reads either document, an Application as a design and a node's bindings as far as they say on their own. Section 7 — the rules a surface calls instead of keeping its own — is `src/ffi/rule.rs` and `src/ffi/rule/node.rs`, forwarding each rule to the crate that owns it (`observe::Scope`, its containment, parts, node and stage, `observe::Health`, `observe::Standing`, `observe::Counted`, `observe::capability`, `node::Stage`, `node::Capability`), one call per export and no rule of its own; section 8, `src/ffi/publication.rs`, reads a publication by `observe::Publication`, and `src/ffi/topology.rs` says what a topology kind, origin or pattern is called (ADR-0027 and ADR-0052, amendments). Section 9, `src/ffi/audit.rs`, forwards `xmip_audit_v1` to `xmip-core-audit`'s `ProgramAudit` (ADR-0062), and `xmip_audit_read_v1` to its reader and `AuditQuery`, answering the header's JSON (ADR-0062, amendment 2026-09-29); `ffi/rule.rs` forwards the one wildcard, `observe::wildcard`, as `xmip_scope_matches_v1`, and whether what a hidden run made is shown, `observe::run::shown`, as `xmip_run_shown_v1` (ADR-0028, amendment 2026-09-30). Section 10 is the routes designer's: `src/design.rs` reads the JSON a surface hands over into `configure`'s types and `src/ffi/design.rs` holds `xmip_application_routes_v1`, `xmip_filter_structure_v1`, `xmip_filter_text_v1` and `xmip_application_edit_v1` (ADR-0064). Section 11 is Events (ADR-0065): `src/ffi/event.rs` holds the six exports, each a thin forwarder into `xmip-core-event`'s process hub, and `src/ffi/event/crossing.rs` reads and writes the header's Event and filter; `src/ffi/event/subscription.rs` holds what an operator lists and does of Event subscriptions — `xmip_event_subscriptions_v1` (the hub's standing, as JSON), `xmip_event_subscription_act_v1` (pause, resume or remove) and `xmip_publication_event_subscriptions_v1` (what a read publication carries) — each forwarding to the event crate (ADR-0065, amendments 2026-09-29 and 2026-09-30). Section 12, `src/ffi/catalogue.rs`, answers `xmip_technology_catalogue_v1` from `src/catalogue.rs`: the technologies a node in this process loaded, each carried with its settings declaration as it loaded (ADR-0064, amendment 2026-09-26). Section 13, `src/ffi/process.rs`, forwards `xmip_process_declare_v1` and `xmip_process_declarations_v1` to `xmip-core-node` (ADR-0053). Section 14 is a node's Subscriptions (ADR-0013, amendment 2026-09-30): `src/ffi/subscription.rs` holds `xmip_subscriptions_v1` (every node's in this process, as JSON), `xmip_subscription_act_v1` (pause or resume; remove is refused, a Subscription being added and removed in the TOML configuration) and `xmip_publication_subscriptions_v1`, each forwarding to the pickup; `src/ffi/order.rs` holds `xmip_order_v1`, the one order a surface over a snapshot leaves for a node, on either noun, forwarded to `observe::Order`.

**A Subscription paused.** `src/pickup.rs` is a node's Subscriptions as an operator sees and pauses them: each taken up from the configuration with the Application that draws it, the file it was read from and its entry there (`src/configured_subscription.rs`, from what `start::read` read), and its standing kept in the node's runtime store (`src/store.rs`: the one its configuration's `[store]` names, over an engine and a key store the program linked — `Linked::engines`, `Linked::key_stores` — refused at phase 3 when the program was not built with them and at phase 9 when it does not open; or the one the program opened itself, `Linked::store`; in memory where the program linked no engine and the configuration names no store). Routing's matches to a paused Subscription are held — persist's `HeldMessage`, numbered in the order held, counted, nothing lost — and a resume lets them go oldest first, what it matches meanwhile joining the end; a running node picks each up on a thread of its own and departs it where its Subscription leads (`src/held_work.rs`: the identity arrival concluded held in its words and read back through the mechanism this node's authenticators declare, departure authorizing again, now). A pause and what it holds survive a restart: the standing is written on every act and hold and read back as the node starts. Every act is audited in the program's audit (`Linked::audit`), and `Running::pickup` hands a node's pickup to its program. `Carried::held` and `Outcomes::held` count what a paused Subscription held.

The C boundary is one folder, `src/ffi/`, and the only place in the runtime that may hold unsafe code (ADR-0050, refined 2026-09-25): the operator's table (`ffi/operate.rs`, over `operator.rs`), starting and validating (`ffi/start.rs`, over `start.rs`), sections 7 to 13, and the loader that opens a module's library (`ffi/loaded_module.rs`, `ffi/loaded_contract.rs`, ADR-0057), which takes a module only when `abi::accepts` — ADR-0012's compatibility rule, beside the descriptor's own in `xmip-core-abi` — does. `test/Unsafe.Test.ps1` holds it. The library stays in the process once loaded (`xmip_operate.h` section 1): its own threads, the audit keeper and an Event listener, outlive every call, so on Windows it pins itself as it loads (`ffi/resident.rs`) and on ELF systems `build.rs` links it `-z nodelete`; `FreeLibrary` and `dlclose` release a reference and never unmap it (ADR-0027, amendment 2026-09-30). Every enum that crosses `xmip_operate.h` as an `int` is converted in one file, `src/wire.rs`. `src/registration.rs` generates what each platform's service manager is told about the Xmip Service and its Host Services, for the installer that registers them.

`architecture.toml` carries the maturity; this file does not repeat it.
