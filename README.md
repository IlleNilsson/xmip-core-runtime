# xmip-core-runtime

The Xmip runtime: a node started from its configuration and the technologies its program links, the message path it runs, and the native library the operator surfaces load.

**A node running.** `running::Running::start(path, linked)` runs ADR-0018's nine startup phases (`src/running.rs`, the phases' work in `src/startup.rs`, their names in `src/service.rs`): it reads the node's configuration and every Xmip Application it binds, each the configuration's `[[xmip_applications]]` section of its name (`start::read`), builds and validates the execution tree — the bound Receive Ports with each Receive Location's interaction and depth, and the Send Ports it takes with their policy, among it — with every Location held to its technology's settings declaration, and refuses — before anything serves — a transport, an accepted mechanism or a filter name the program was not built with, a contract at a Location (arrival holds no Stream to one yet), and a Module needing a Host Service in a process of its own. It plans the Host Services the started Modules need (`src/host.rs`, one host-type rule: what a Module is written in), loads each technology the configuration uses once — carrying its declaration into the catalogue — and opens each `[[modules]]` library once through the C ABI (`src/library.rs`, behind `dynamic-loading`), registers every capability once (`src/capability_registry.rs`), builds each Location's transport once from its address and settings and gives it the node's location as it does (`transport::Configured::open`, then `Configured::on_node` with `running::publication::location`, the owner's *Option A*, 2026-10-03 — the file transport claims in that name and returns what it still held there; so a Receive Location keeps its listener or session between receives), reaches Xmip Storage (`src/storage.rs`, below), builds the `Runtime` once — the route gathering compiled then (ADR-0066) — and serves every Receive Location on a thread of its own: `Receiving::serve` (`src/receiving.rs`) takes what arrives and carries each arrival on the Location's pool (`src/pool.rs`: a dynamic, bounded pool of scoped threads, never below one, growing while work waits up to `pool::Limits::per_hardware_thread` — for a Receive Location twice the machine's hardware threads (`pool::hardware_threads`), calculated as the node starts — and shrinking after a minute idle; a piece of work that panics ends that piece, not its thread, and a thread is counted out however it ends), one thread carrying one arrival through the whole cycle and telling its far end the verdict — a carry that panics tells it `Failed` on the way out, so the far end keeps the Stream to send again and the Location settles the arrival as failed rather than waiting for it, and its stop with it — the arrivals of one receive told in the order they came and all of them before the transport is asked again; `message_path::carry` runs each Stream through arrival, routing and Publication into the Ledger — the receive cycle sends nothing — and `Carried::cycle` says whether the receive cycle completed — accepted and durable, to be acknowledged — or was refused or failed (`ReceiveCycle`). `stop` drains: each Receive Location takes nothing more once its current receive returns (the technology's own wait bounds it), what it took is carried whole, then the transports and loaded Modules are let go. `outcomes` and `snapshot` say what became of every Stream and what the node is doing; `publication` (`src/running/publication.rs`) is that snapshot at the node's `location`, `xmip:///<cluster>/node/<name>` — itself, its System Process, what it declares, each module, Location and Subscription, the figures at the stage that counts each kind, its Subscriptions' standing — with the node drawn by `observe::topology::draw` and `party`, the Party on each side `any-party` while a configuration can name none; `running::publication::stopped` is what it leaves once drained, the node Done and its pauses standing. `xmip-service` writes it to `<data>/snapshot.toml` (ADR-0018, amendment 2026-09-30).

**What the program links.** The runtime names no technology (`architecture.toml`: a platform service depends on no technology repository). The program that starts a node hands over what it was built with as `linked::Linked` — its transports (`LinkedTransport::of::<T>()` over `transport::Configured`), route technologies, authenticators, policies and identifiers — and the node takes what its configuration names (ADR-0025). ADR-0018's amendment of 2026-09-26 makes that program `xmip-service`, an executable of the estate's root crate that links technologies by build feature. It was built on 2026-09-28. It runs a node until the operating system's service manager or the console stops it, then calls `Running::stop`. The runtime's own tests are a program too: they link `xmip-core-transport-tcp` and start a node that receives and sends over loopback. The stand-ins they run a node's gates with — an authenticator verifying with the verdict it was given, a policy allowing what the gates authenticated — are `fixture`, placed once behind the `test-support` feature, which only the crate's dev-dependency on itself enables, so its unit tests and `tests/ledger` share them. `Running::cluster` and `Running::node` give the node's place, and `Running::location` the location `xmip-service` declares, `xmip:///<cluster>/node/<node>` (ADR-0053).

**As a service.** `src/registration.rs` is the one place that writes what a service manager is told about a node's Xmip Service: a systemd unit (`Type=notify`, `Restart=on-failure`, `RestartPreventExitStatus=` the refused exit code `REFUSED`), a launchd property list, or the `sc.exe create` arguments. It runs `xmip-service --configuration <path>` under the name `node_service_name(node)`, `xmip-<node>`, and quotes a path that has a space. `xmip-service --definition` prints it. `src/service_control.rs` asks this platform's service manager to start or stop a node's installed service by that name: `sc.exe`, `systemctl --no-block` or `launchctl`, chosen at compile time. It returns when the manager has accepted the request, and a manager's refusal comes back in the manager's own words. Nothing in the runtime applies a registration or restarts a service.

**The message path.** Arrival (`src/arrival.rs`) runs the transport gates against the Receive Location's `ReceiveGate` — the closed set of mechanisms its configuration's `accept` names (ADR-0019 clause 1), each verified by a linked authenticator — then creates the Message, runs the message gates, promotes every name the Subscriptions' filters use through the `route::Gathering` the Runtime was built with (a bare name is context, a prefixed one is read by its technology, a Null is absent, bytes refuse the Message; ADR-0046), opens the Journey and publishes. **The Ledger** (`src/ledger.rs`, `runtime-model.md` sections 3 and 5): once the transport gates pass — a refusal keeps nothing — arrival reads the arrival's body — `receive::ReceivedStream::body`, the transport's reader — into Xmip Storage in chunks, unsynced, by `ledger::write_stream(storage, stream, &mut reader, chunk)`, and from there holds the Stream as kept (`ledger::Kept::stream`: `stream::Stream::kept` over `ledger::Chunks`, read back a chunk at a time up to the first it does not hold, where the Stream ends, and held to the length the Stream's own record keeps — written once, with its last chunk, the one home of its length and of the SHA-256 digest `write_stream` takes of its bytes as they pass once (ADR-0070), which every Message referring to the Stream refers to; the reading is Xmip Storage's one chunk reader, `persist::storage::ChunkReader`; a chunk lost after Publication is refused in words), so nothing holds the whole Stream where the far end streams it: a gate that reads the content whole loads it once (`Stream::load`), a Stream that could not be read back fails the cycle rather than route on nothing (`Stream::unread`), and departure loads it where its transport sends it whole; `tests/ledger/bounded.rs` carries 64 MiB in chunks holding a few chunks at most; `carry` then writes the Publication — the Message record (`message::Message::record`), a Journey per matched Subscription and per Send Port it reaches — one per Port of a Send Port Group, each naming its `send_port` (`ledger::opened`, over `Pickup::reaches` and `ConfiguredSubscription::ports`; `journey::Journey::matched`, its `record`) and the Publication's audit record in the audit capability's form, carrying the Message in full and every Stream its Sections are over, whose bytes the audit keeper keeps beside it (ADR-0070; `ledger::audited`, `tests/ledger/audited.rs`) — as one write whose one sync makes the chunks durable with it, before the cycle is reported completed; a writer's audit chain as Xmip Storage keeps it is walked by `ledger::verify_audit_chain` — each kept record in its number's order, its Streams' records and its body read a chunk at a time and held to its digest, digested by persist's `chain_digest` and walked by `xmip-core-audit`'s `audit_chain::walk`, which says where it breaks (ADR-0070 clause 5; `src/ledger/audit_chain.rs`); every record of a Journey, a Message and an audit record the runtime writes is made in one place, `ledger::journey_record`, `ledger::message_record` and `ledger::audit_entry` (`src/ledger/record.rs`), carrying beside its body the facts Xmip Storage keeps in searchable columns, found through `XmipStorage::query` (proposed 2026-10-09; `tests/ledger/searched.rs`); a Message nothing matched is kept with its entry in the node's Dead Message Queue in that same write (`src/dead_message.rs`: the receive context, what the gates concluded, the promoted properties `Arrived::Unroutable` carries, and every Subscription's decline; `tests/ledger/dead_message_queue.rs`). **The Dead Message Queue** is read and replayed through the pickup (`src/pickup/replay.rs`): `Pickup::dead_messages` reads the oldest of it for the node's snapshot (`pickup::PUBLISHED`, a hundred), and `Pickup::replay`, the Operator's act, routes an entry's promoted properties against the node's Subscriptions of now and writes the Journeys it opens (`ledger::opened`, the one place a Publication's Journeys are opened), each held in its Subscription's queue and picked up as a resume picks up, with the entry taken out and its audit record, carrying the Message as the Ledger keeps it, as one write, once; a Message that still matches nothing stays, refused with every decline. An order on the noun `dead-message` reaches it as Pause does (`xmip-service`'s `orders.rs`, the Playground's `operator_orders.rs`). Xmip Storage failing either is `Arrived::Failed`, counted as `Outcomes::failed`, and not acknowledged. The chunk is `[tuning] segments` TCP segments of `[tuning] tcp_segment` bytes, by default `ledger::CHUNK`: 44 (`ledger::SEGMENTS`) of 1460 (`transport::TCP_SEGMENT`), 64,240 bytes. **`[tuning]`** (`src/tuning.rs`; ADR-0031, amendment 2026-10-03) is every outward and hardware assumption the node runs by — the chunk, a Receive Location's pool (`receive_threads_per_hardware_thread`, default `pool::RECEIVE_THREADS_PER_HARDWARE_THREAD`, and `receive_idle`, default `pool::RECEIVE_IDLE`), the Send pool and its claims (`send_threads_per_hardware_thread`, `send_idle`, `send_lease`, `send_scan`, defaults `send_step::SEND_*`) and the Storage client's `storage_timeout` and `storage_pass_over` (persist's `client::TIMEOUT` and `client::PASS_OVER`) — declared once as `tuning::TUNING` in `xmip-core`'s settings shape, read through it into the execution tree (`ExecutionTree::tuning`) and refused at phase 3 where a key is unknown, of the wrong kind or out of bounds; the constants are its defaults only. `start::validate` validates a cluster's `xmip.toml` node by node, each slice as `configure::slice` writes it, every problem opening with the node's location. **The send step** (`src/send_step.rs`, `runtime-model.md` section 10, built 2026-10-03) sends every Journey from the Ledger: the Publication keeps each Journey that is not held in the queue of where it leads (`sending::queue`, the name-based identifier of `<cluster>/<kind>/<name>`, the same on every node) and, where this node sends that Send Port and it is not Sequential, claims it in the same write and hands it to the node's Send pool in memory (`SendStep::line_up`, `SendStep::handed`), so the send starts without a sync of its own — as many as the pool admits; `send_step::dispatch` runs the pool (`[tuning] send_threads_per_hardware_thread`, `send_idle`), and each pass (`send_step::send`) tries the Send Port's Locations in order, retrying and failing over as its policy says (`sending::Port`), and hands on in one write — Completed and out of its queue, Failed with why and kept in its queue for an operator (blocking its sequence where a Sequential Port's `on_failure` says `block`), or Recovering with its claim kept to its due time, a retry's backoff holding no thread — its tries the Journey's `attempts`, so a retry's count survives a restart (built 2026-10-04). An Operator's **Retry** and **Dismiss** of a failed Journey (`SendStep::act`, `src/send_step/journey_act.rs`; `xmip_operate.h` section 16, `src/ffi/journey.rs`; an order on the noun `journey` through `xmip-service`'s `orders.rs`) are each one hand-on under a claim, audited: Retry writes it Active and moves it to the end of its Port's queue (`HandOn::requeued`), keeping its place where it blocks a Sequential Port; Dismiss writes it Dismissed and takes it out, so its sequence goes on (`tests/ledger/journey_act.rs`). A Send Port Group's Journeys are one per Port, each sent alone (`tests/ledger/send_group.rs`). As the node starts and every `send_scan` after, each queue this node sends is read and every Journey no live claim holds is claimed and sent (recovery, and failover by a lapsed claim); a Sequential Send Port sends one Journey of each sequence (its `order_key`'s value) at a time, oldest first; in-flight claims are renewed on a thread of their own every third of a lease, and a stop gives back the claims of what waits. **A renewal's answer is acted on** (`src/send_step/renewal.rs`, corrected 2026-10-06): one that finds the claim another's stops every further Location of the pass and writes nothing, the loss counted at the Port and audited; one Xmip Storage does not answer leaves the claim unconfirmed — the Port Done from the first, a flat-out error — and Locations are tried only while a lease from the request that last confirmed it lasts, on the node's own clock (`Departure::until`, `SendStep::holds`), past which it is presumed lost and audited once; a send already under way keeps its Journey's identifier as the far end's deduplication key (`tests/ledger/send_claim.rs`). A Publication's claims are sent from here only where Xmip Storage's answer says the node holds them (`SendStep::confirmed`), so a Publication asked again after a lost answer sends nothing another node sent meanwhile (`tests/ledger/send_raced.rs`, over `fixture::Failing::lose_answer`). **Admission is the one door to the Send pool** (`src/send_step/admission.rs`, corrected 2026-10-06): a Publication, a resumed Subscription's move (`held_work::pick_up`) and a scan each claim a Journey only under a place the pool admits (`SendStep::admit`) — its most threads less every Journey the node owns, a retry waiting for its due time among them, and every place admitted and not yet owned (`SendStep::room`) — and give back a place a write did not take; what has no place stays durable and unclaimed in its queue, which is read again the moment a place frees, so a slow far end leaves its backlog in the Ledger and the node's memory stays bounded by its threads; a scan of a queue that is not ordered claims what it finds on the send thread its place was admitted for, so a backlog's claims share their commits rather than wait one by one on the dispatching (`send_step::dispatch`'s `take`; `tests/ledger/send_bounded.rs`). An act or a Sequential scan decides on a Journey read again under its claim, refusing or passing over one another writer moved after the first read (`tests/ledger/send_raced.rs`, over `fixture::Failing::before`, which lets another writer in between two calls by order, never by timing). A send whose thread panics is settled on the way out (`send_step::dispatch`'s `Sending`): written Failed with why, its claim ended, counted and audited. `SendStep::figures` counts, as history since the node started, what each Send Port sent and failed, the claims it lost, and the last Journey that failed with its reason; and, as its queue stands now, what waits for a retry's due time, every Journey a scan read Failed in its queue — one that failed before a restart or on another node among them — and whether one blocks its sequence, and the claims whose renewal Xmip Storage has not answered, with since when. The snapshot publishes a record at `<node>/send/<Port>` for every Send Port the node sends, apart from its Send Locations — Done while failed Journeys wait in its queue, most severe where one blocks its sequence, and Done while a claim's renewal is unanswered, its evidence naming Xmip Storage and since when; Fine once neither is — and every Port's failed Journeys (`PortFigures::published`, `observe::FailedJourneys`): `count` now, zero where none, `blocked`, the oldest hundred, and `last_failure` apart, as history; `SendStep::failed_journeys` reads them from Xmip Storage a page at a time, for `xmip_failed_journeys_v1` (`tests/ledger/send.rs`, `tests/ledger/send_killed.rs`). A Receive Location's far end that could not be told in a way asking again may mend is audited once for each reason, with the Location and why (`Receiving::audit`, `tests/ledger/untold.rs`). **How a node reaches Xmip Storage** (`src/storage.rs`): the Xmip Storage its program opened itself (`Linked::storage`: a test's Storage node, or a client of the Storage nodes the program built with the identity it presents); otherwise, where `[storage]` lists no Storage node, the node is its own embedded Storage node — `RocksDB` at `<data>/storage/runtime` and `SQLite` at `<data>/storage/administration.sqlite` (`Linked::engine`, `Linked::administration`), sealed under the key store `[store]` names with the key-encryption key `storage` — refused at phase 3 where the program was not built with both engines and at phase 9 where they do not open; a node listing Storage nodes is refused at phase 3 unless its program handed it the client, since the identity it presents to them is not configurable yet. `Running::storage` says which, and the chunk. Departure (`src/departure.rs`) is one pass of a Journey to its Send Port: its active Send Location (`src/sending.rs`: a bound Send Port is the Send Location of its name, or those its `send_locations` names in order; a Send Port Group's Ports each by a Journey of their own), `departure::Progress` keeping where it stands between passes, from and into the Journey's `attempts`; it authorizes again, resolves whose identity the chain declares (ADR-0006) and sends through the Location's transport with the Journey's identifier as its deduplication key (`transport::Transport::send_keyed`, runtime-model section 15); a Work Process destination is `ProcessNotRun`, since a Process is compiled at design time and none is built (ADR-0066 clause 4). What both halves share — the `Runtime`, `Parties` and `PartyDirectory` — is `src/message_path.rs`; its `clock` is read at each gate, and a running node's is `xcore::SystemClock`. The Message treatments are `xmip-core-message`'s; `src/generation.rs` keeps what a generation is.

**For a surface.** Its native library is what the operator surfaces load (`xmip_operate.h`). `start::start`, behind `xmip_start_v1`, is the first three phases alone: it validates and plans a node against the technologies this runtime carries and says in every record that nothing runs, since a surface's process links no technology (whether it may run a node at all is open problem 20); `xmip_validate_v1` reads a node's configuration, its bindings with the Application sections they bind, or a cluster's `xmip.toml` node by node. Section 7 — the rules a surface calls instead of keeping its own — is `src/ffi/rule.rs` and `src/ffi/rule/node.rs`, forwarding each rule to the crate that owns it (`observe::Scope`, its containment, parts, node and stage, `observe::Health`, `observe::Standing`, `observe::Counted`, `observe::capability`, `node::Stage`, `node::Capability`), one call per export and no rule of its own; section 8, `src/ffi/publication.rs`, reads a publication by `observe::Publication`, and `src/ffi/topology.rs` says what a topology kind, origin or pattern is called (ADR-0027 and ADR-0052, amendments). Section 9, `src/ffi/audit.rs`, forwards `xmip_audit_v1` to `xmip-core-audit`'s `ProgramAudit` (ADR-0062), and `xmip_audit_read_v1` to its reader and `AuditQuery`, answering the header's JSON (ADR-0062, amendment 2026-09-29) — with each writer's audit chain walked over the file as it is now where the query asks `verify` (ADR-0070 clause 5); `ffi/rule.rs` forwards the one wildcard, `observe::wildcard`, as `xmip_scope_matches_v1`, and whether what a hidden run made is shown, `observe::run::shown`, as `xmip_run_shown_v1` (ADR-0028, amendment 2026-09-30). Section 10 is the designer's, over the cluster's one `xmip.toml`: `src/design.rs` reads the JSON a surface hands over into `configure`'s types and `src/ffi/design.rs` holds `xmip_cluster_views_v1` (the file as one view per artifact kind, an Xmip Application's routes among them), `xmip_filter_structure_v1`, `xmip_filter_text_v1`, `xmip_cluster_edit_v1` and `xmip_cluster_slices_v1`, each node's document by `configure::slice`, a node's own document refused (ADR-0064, amendment 2026-10-03; ADR-0031, amendment 2026-10-05); the views say `document`, `cluster` or `node`, by `configure::document_kind`, so the Operation Desktop offers no node's file for editing. Section 11 is Events (ADR-0065): `src/ffi/event.rs` holds the six exports, each a thin forwarder into `xmip-core-event`'s process hub, and `src/ffi/event/crossing.rs` reads and writes the header's Event and filter; `src/ffi/event/subscription.rs` holds what an operator lists and does of Event subscriptions — `xmip_event_subscriptions_v1` (the hub's standing, as JSON), `xmip_event_subscription_act_v1` (pause, resume or remove) and `xmip_publication_event_subscriptions_v1` (what a read publication carries) — each forwarding to the event crate (ADR-0065, amendments 2026-09-29 and 2026-09-30). Section 12, `src/ffi/catalogue.rs`, answers `xmip_technology_catalogue_v1` from `src/catalogue.rs`: the technologies a node in this process loaded, each carried with its settings declaration as it loaded (ADR-0064, amendment 2026-09-26). Section 13, `src/ffi/process.rs`, forwards `xmip_process_declare_v1` and `xmip_process_declarations_v1` to `xmip-core-node` (ADR-0053). Section 14 is a node's Subscriptions (ADR-0013, amendment 2026-09-30): `src/ffi/subscription.rs` holds `xmip_subscriptions_v1` (every node's in this process, as JSON), `xmip_subscription_act_v1` (pause or resume; remove is refused, a Subscription being added and removed in the TOML configuration) and `xmip_publication_subscriptions_v1`, each forwarding to the pickup; `src/ffi/order.rs` holds `xmip_order_v1`, the one order a surface over a snapshot leaves for a node, on either noun, forwarded to `observe::Order`.

**A Subscription paused.** `src/pickup.rs` is a node's Subscriptions as an operator sees and pauses them: each taken up from the configuration with the Application that draws it, the configuration it is a section of and its entry there (`src/configured_subscription.rs`, from what `start::read` read), and its standing kept in the node's runtime store (`src/store.rs`: the one its configuration's `[store]` places, over RocksDB, the one engine (ADR-0015, amendment 2026-10-01), and a key store the program linked — `Linked::engine`, `Linked::key_stores` — refused at phase 3 when the program was not built with them and at phase 9 when it does not open; or the one the program opened itself, `Linked::store`; in memory where the program linked no engine and the configuration names no store). Routing's matches to a paused Subscription are held — persist's `HeldMessage`, numbered in the order held, counted, nothing lost — and a resume lets them go oldest first, what it matches meanwhile joining the end; a running node picks each up on a thread of its own and moves it, in one hand-on, to the queue of the Send Port its Subscription leads to, from which the send step sends it (`src/held_work.rs`: the identity arrival concluded held in its words and moved with it, read back through the mechanism this node's authenticators declare, departure authorizing again, now). A pause and what it holds survive a restart: the standing is written on every act and hold and read back as the node starts. Every act is audited in the program's audit (`Linked::audit`), and `Running::pickup` hands a node's pickup to its program. `Carried::held` and `Outcomes::held` count what a paused Subscription held.

The C boundary is one folder, `src/ffi/`, and the only place in the runtime that may hold unsafe code (ADR-0050, refined 2026-09-25): the operator's table (`ffi/operate.rs`, over `operator.rs`), starting and validating (`ffi/start.rs`, over `start.rs`), sections 7 to 13, and the loader that opens a module's library (`ffi/loaded_module.rs`, `ffi/loaded_contract.rs`, ADR-0057), which takes a module only when `abi::accepts` — ADR-0012's compatibility rule, beside the descriptor's own in `xmip-core-abi` — does. The library stays in the process once loaded (`xmip_operate.h` section 1): its own threads, the audit keeper and an Event listener, outlive every call, so on Windows it pins itself as it loads (`ffi/resident.rs`) and on ELF systems `build.rs` links it `-z nodelete`; `FreeLibrary` and `dlclose` release a reference and never unmap it (ADR-0027, amendment 2026-09-30). Every enum that crosses `xmip_operate.h` as an `int` is converted in one file, `src/wire.rs`. `src/registration.rs` generates what each platform's service manager is told about the Xmip Service and its Host Services, for the installer that registers them.

`architecture.toml` carries the maturity; this file does not repeat it.
